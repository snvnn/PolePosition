# GUI 실행 규약

2026-10-03. 기존 모방학습·오프라인 평가·기록 수집·저속 모델 평가/주행을 연결했다.
실제 관리 주행의 F8·전면 이탈 정지와 장치 해제를 확인했다. 기존 GUI에
`강화학습 자료 준비`, `강화학습 사전학습`, 수동 준비 기반 `강화학습`을 연결했다.
강화학습 워커는 별도 `.venv-controller`를 사용한다. 실제 정책 제어·경험 저장·정차 후 SAC 갱신과 재개를 검증했으며 자동 메뉴 초기화는 후속 과제다.

## 실행

저장소 루트에서 `.venv-training/Scripts/python.exe -m TrainingController`.
바탕화면의 `PolePosition Controller` 바로가기로도 실행한다.
바로가기를 다시 만들려면 `TrainingController/install_shortcut.ps1`을 실행한다.
다른 프로그램을 가리키는 같은 이름의 바로가기는 덮어쓰지 않는다.
GUI는 Tkinter/ttk로 구성한다. 학습은 기존 고정 환경의 별도 프로세스에서 실행한다.
검증된 데이터 폴더와 학습 TOML을 선택해 시작한다. 이어서 학습은 `last.pt`를 선택하며
기존 학습기의 해시 검증 및 새 결과 폴더 생성 규칙을 유지한다.
`새 학습 상한(epoch)`은 빈칸이면 TOML 설정을 사용하고, 1~200을 입력하면 기존 실행부의
`epoch_limit`에 전달한다. 실제 상한은 TOML의 max_epochs와 입력값 중 작은 값이며 기존 조기
종료 조건도 유지한다. 원본 TOML이나 학습 로직은 수정하지 않는다. 이 값은 이번 새 학습에만
적용되므로 `이어서 학습`은 체크포인트에 저장된 학습 설정을 그대로 사용한다.

처음 작업을 선택하면 해당 작업의 기존 TOML 경로가 선택된다. 이후 작업을 오가도 창에서
선택한 작업별 TOML 경로를 유지한다. 현재 작업에 필요한 입력만 활성화하고 나머지는 비활성화한다.
실게임 작업의 시작 버튼은 `준비 — F7 대기`, 오프라인 작업은 학습/평가 시작으로 표시한다.
`이어서 학습`은 모방학습과 강화학습 사전학습에서, 이전 통과 주행 입력은 `drive` 모드에서만 활성화한다.
실게임 강화학습은 실행부 미연결 설명을 표시하고 시작을 비활성화한다. 오프라인 자료 준비·사전학습은 실행할 수 있다.
자료 준비가 완료되면 새 데이터 경로를 자동 입력한다. 사용자는 사전학습 작업으로 전환하여 시작한다.
사전학습 결과의 체크포인트 선택은 해당 작업과 기본 TOML로 전환한다. [v2 실행 규약](TrainingEnvironmentSpecification.md)을 참조한다.
오프라인 평가의 모델 입력은
완료된 모방학습 결과 폴더, 실게임 평가·주행의 모델 입력은 검증된 export 폴더다.
주행에는 검증된 경로 상태 폴더와 보정 JSON도 필요하다. 기존 `shadow/drive`,
5·10·15초 모델 인계 단계와 이전 결과 검증을 그대로 사용한다. 이 단계는 새 RL 속도 단계가 아니다.
`준비`는 실게임 기록·주행을 F7 대기로 만든다. ACC를 전면으로 두고 F7로 시작하고 F8로 중지한다.
관리 채널에는 원격 시작 명령이 없다.

## 관리 채널 v1

UTF-8 JSON Lines를 stdin/stdout으로 주고받는다. 모든 메시지는 `version: 1`이다.
관리 채널로 조향·페달 값을 보내지 않는다. stdout은 이벤트 전용이고 기존 학습 로그는 stderr로 배출한다.

- 명령: `command: heartbeat`, `command: stop`.
- 상태: `event: state`, `state: training|evaluating|waiting_f7`.
- 주행 준비 검사: `event: state`, `phase: preparing`, `preparation: {check, state}`.
  `check`는 `config|path|model|driver|calibration|hotkeys`, 검사 상태는 `checking|verified|failed|cancelled`다.
  실제 검사 호출 전후의 결과를 전달하며, GUI의 별도 준비 검사 기록에 유지한다.
  파일 검증 통과는 실시간 경로 추적 성공 또는 주행 허가를 의미하지 않는다.
- 학습 진행: `event: progress`, `epoch`, `updates`, `loss`, `elapsed_seconds`, `result_dir`.
- 실게임 진행: `event: progress`, `phase`, `connection`, `identity`, `speed_kmh`, `elapsed_seconds`, `result_dir`.
  주행은 추가로 `fresh`, `tracking_ready`, `foreground`, `vjoy`, `calibration`, `reason`, `controller_reason`을 전달한다.
  `controller_reason`은 기존 제어기의 상태 이유이며 종료 이유 `reason`과 구분한다.
  GUI는 ACC 전면 여부와 제어 상태를 표시하고, PID 출발 중 `waiting_forward_gear`를
  ‘전진 기어 대기 — ACC에서 1단 확인’으로 표시한다. 정지 처리 단계는 이 표시로 덮어쓰지 않는다.
- 결과: `event: finished`, `state: completed|stopped|failed|needs_attention`, `reason`, 선택적/nullable `result_dir`.

GUI 갱신은 200ms 간격이다. GUI 이벤트 루프가 500ms마다 생존 신호를 보낸다.
준비 검사 전환은 개별 상태 이벤트이며, 주기적 주행 표시는 계속 최대 5Hz다.
준비 도중의 중지·통신 단절·시간 제한은 각 검사 전후에 확인한다. 중지가 확인되면 다음 검사를
실행하지 않는다. 장치 획득 직전의 보정/경로 재검증에도 이 확인을 적용한다.
사용자 취소는 `stopped`, 통신 실패는 `failed`로 보고하며 오류 원문은 결과 이유에 남긴다.
준비 도중 결과 이벤트 없이 종료하면 확인 중인 항목을 통과로 바꾸지 않고 결과 미확인으로 표시한다.
3초 동안 신호가 없거나 입력 채널이 닫히면 실행부에 중지를 요청한다.
이 간격은 GUI 생존 감시의 구현값이며 기존 차량 입력 만료·F8·전면 이탈 규약을 대체하지 않는다.
중지 요청은 미니배치 경계에서 처리하고 마지막 완료 epoch를 보존한다.
오프라인 실행에서 사용자 중지·설정 시간 제한은 `stopped`, 연결 단절·생존 신호 만료·통신 규약
오류는 `failed`로 구분한다. 결과 폴더를 반환한 실패도 최근 결과에 남긴다.
실행부가 진행 메시지로 결과 폴더를 알린 뒤 예외가 발생하거나, 반환된 폴더의 manifest를
읽지 못하는 경우에도 이미 알려진 폴더를 실패 결과에 포함한다. 생성 위치를 한 번도 받지
못한 실패에서는 폴더를 추측하지 않는다. 결과 위치 보존이 완료 판정이나 자동 재실행을 뜻하지 않는다.
중지 원인이 없으면 기존 결과의 오류 또는 종료 이유를 표시한다.
오프라인 평가 중지는 추론 배치·결과 행 경계에서 확인하며 미완료 결과는 완료 처리하지 않는다.
Rust 주행 감시기는 기존 정지·제동·해제 상태기로 들어간다. 강제 종료를 정상 종료로 표시하지 않는다.
진행 알림은 제한된 큐에서 일부 생략할 수 있지만 최종 결과는 별도로 보존한다.
Python 수신부는 Tk가 소비하는 진행 필드의 형식을 확인한다. 불완전한 epoch 진행,
유한하지 않은 숫자, 잘못된 차량 정보·준비 검사·결과 경로 형식은 실패로 처리하고 중지를 요청한다.
Python 관리 명령도 Rust와 같이 버전/command 두 필드만 허용하며 읽기 길이를 제한한다.
새 자식의 읽기 스레드를 시작하기 전에 이전 작업의 신호를 초기화해, 시작 직후의 중지 요청이
이후 초기화에 의해 지워지지 않도록 한다.
프로세스 종료 코드와 최종 이벤트를 함께 확인하며 결과 없는 종료를 성공으로 취급하지 않는다.
자식과 출력 읽기가 종료된 뒤 파이프를 정리할 때 발생하는 이미 닫힌 파이프 오류는 무시한다.
최종 결과를 전달하고 프로세스 소유를 해제하는 절차는 계속 수행한다. 실행 중 통신 오류를
무시하거나 결과 없는 종료를 성공으로 바꾸는 처리는 아니다.

동시에 하나의 자식만 실행한다. 실행 중 데이터·체크포인트·설정을 잠근다.
창 닫기는 정상 중지를 요청하고 실제 자식 종료 후 창을 닫는다.
실제 모의 자식이 중지 처리에 시간을 쓰는 동안 창을 유지하고, 최종 중단 이벤트와 프로세스
종료를 받은 뒤 창을 닫는 Tk 통합 검사를 포함한다.
자동 보고서 열기나 알림창은 사용하지 않는다.
최근 결과는 학습·평가·기록·주행 폴더를 합쳐 수정 시각 내림차순으로 최대 80개 표시한다.
새 결과를 추가해도 기존 목록 선택을 유지한다. 보고서가 없는 결과에서는 보고서 버튼을 비활성화한다.
`체크포인트 선택`은 선택한 결과의 `last.pt` 경로만 입력하며 학습을 자동 시작하거나 파일 내용을 읽지 않는다.
실제 재개 검증과 새 실행 폴더 생성은 기존 학습 실행부가 수행한다.
작업 중에는 결과 열기·체크포인트 선택도 잠가 실행 설정이나 ACC 전면을 바꾸지 않도록 한다.
창 파괴 시 예약된 다음 GUI 갱신을 해제한다.

## Rust 관리 모드

`poleposition-recorder --managed --config FILE --duration SECONDS`.
`poleposition-actuator policy --managed --managed-seconds SECONDS`에 기존 경로·모델·보정 인자를 함께 전달한다.
GUI는 shell 없이 인자 배열로 실행한다. `--managed`가 없으면 기존 CLI 방식으로 실행한다.
F7/F8은 실행 중인 Rust 기록기 또는 감시기가 한 번만 등록하고, 정책 생산 자식은 등록하지 않는다.
공유 Windows 시계·전면 검사·핫키 코드는 `poleposition-management` 라이브러리에 모았다.

관리 진행 출력은 별도 쓰기 스레드와 제한된 큐를 사용하며 100Hz 감시 루프에서 출력 대기를 하지 않는다.
GUI 명령 쓰기도 별도 스레드에서 처리한다. 해당 스레드는 GUI를 대신해 생존 신호를 생성하지 않는다.
Rust 관리 명령은 최대 4096바이트이며 버전·명령·허용 필드를 검사한다.
시간 제한은 대기 시간을 포함해 최대 7200초다. 차량 정지·저장 마무리는 제한 도달 이후에도 정상 절차를 따른다.
기록기는 F7 전에는 결과 폴더를 만들지 않는다. 주행은 기존 준비 검증과 감시기 준비 절차를 유지한다.

## 아직 연결되지 않은 실행

SAC 주행·학습·재개와 별도 환경은 아래 수동 준비 기반 실행에 연결했다. 자동 메뉴 초기화와 속도 단계 상승 평가는 후속 범위다.
유휴 상태에서는 `poleposition-telemetry --managed`가 읽기 전용으로 ACC 연결·차량·트랙·관측 갱신과
관측 경과 시간을 최대 5Hz로 전달한다. 이 진단은 핫키를 등록하거나 vJoy를 획득하지 않는다.
작업을 요청하면 진단의 실제 종료를 확인한 뒤 작업을 시작한다. 진단 종료 대기 중 취소/창 닫기는
예약된 작업을 제거한다. 작업이 끝난 뒤에는 읽기 전용 진단만 다시 시작하며 주행 작업을 자동 재시작하지 않는다.
진단 자체가 실패하면 반복 실행하지 않으며 `연결 다시 확인`으로 재시도한다.
유휴 진단의 관측 갱신 기준은 기존 주행 감시기의 100ms 기준을 사용하되, 실제 주행 허가는
경로·보정·입력 상태를 확인하는 기존 Rust 감시기가 판단한다. 유휴 진단은 주행 준비 완료 판정이 아니다.
경로·vJoy·보정 상세 상태는 기존 실게임 준비/주행 과정에서 확인한다.
모의 검사와 F7 대기 검사 결과는 실게임 주행 중 종료 또는 주행 성능의 근거가 아니다.
실제 ACC에서 관리 기록기의 F7 시작/F8 중지 및 전면 이탈 종료는 확인했다.
각각 `stopped / f8`, `needs_attention / foreground_lost`를 전달했고 정상 저장과 누락 0을
검증했다. 차량 제어 없이 수행한 기록 시험이므로 주행 중 제동/정지/장치 해제 확인과 구분한다.

## GUI 전체 연결 검사

`TrainingController.test_workflow`는 임시 합성 자료로 실제 Tk 이벤트 루프·관리 프로세스·기존
모방학습 실행부를 연결한다. 완료 epoch가 표시된 후 GUI 중지를 요청하고 미완료 결과와
보존된 체크포인트를 확인한다. GUI 결과에서 체크포인트를 선택해 별도 폴더로 재개하고,
원본 체크포인트가 바뀌지 않았는지 확인한다. 이어서 오프라인 평가의 완료·HTML 보고서·최근
결과 반영을 검사한다. 실제 사람 자료의 학습이나 ACC 주행 검증을 대체하지 않는다.


## 수동 준비 기반 강화학습 실행

`강화학습` 항목을 연결했다. 모델은 v2 사전학습 결과, 경로·보정·주행 설정은 검증된 기존 파일을 선택한다. 주행 모드 `verify5`, `verify10`, `verify30` 통과 후 `train`을 선택한다. 완료된 검증의 `sac-session` 폴더를 이전 결과로 사용하며 GUI가 다음 검증 단계와 경로를 채운다. 준비 버튼은 장치/경로/모델을 검사하고 F7을 기다린다.

각 회차의 수동 준비, 주행, 정차 확인, 경험 검증, 학습, 저장을 표시한다. F8 또는 GUI 중지는 배치 전체를 중단하며 스스로 재시작하지 않는다. 온라인 체크포인트는 파일이 아닌 폴더이며 `이어서 학습`에서 선택한다. 자동 메뉴 초기화는 요구하지 않는다.

개발 검증용 `--preset <JSON> --prepare`는 GUI 항목을 미리 채워 준비 검사를 실행한다. F7을 생성하지 않는다.
