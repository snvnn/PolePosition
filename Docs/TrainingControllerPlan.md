# 폴포지션 GUI 학습 컨트롤러 개발 계획

작성일: 2026-10-01 (Asia/Seoul)

상태: **계획 저장 완료 / 구현 미착수 / 사용자 요청으로 후속 작업 보류**.

이 문서는 대화에서 정리한 개발 계획을 보존한다. 아래 기능과 검증은 앞으로 수행할 작업이며 완료 실적이 아니다. 재개 시 첫 작업은 **기존 프로그램의 실행 관리 규약과 최소 GUI 연결**이다. 이 계획을 저장하면서 프로그램 구현, 의존성 설치, 학습 또는 실게임 시험을 시작하지 않았다.

## 1. 목표와 구성

**채팅이나 터미널 조작 없이 데이터 수집·학습·평가·실게임 실행을 관리하는 Windows 프로그램을 만든다.** 화면은 최소화하고, 기존 Rust 모듈을 실행·관리하는 역할에 집중한다.

대화에서 선택한 범위를 다음과 같이 반영한다.

- 기존 모방학습과 새로운 강화학습을 모두 관리한다.
- 강화학습은 조향·가속·브레이크를 다루며, 완주와 레이싱 속도까지의 성능 향상을 목표로 한다.
- 게임 초기화와 다음 회차 시작을 자동화한다.
- 작업은 한 번에 하나씩 실행한다.
- 자동 실행은 기본 **최대 10회 또는 2시간**이며, 먼저 도달하는 조건에서 종료한다.
- ACC를 전면에 유지하고 **F7 시작 / F8 중지**를 사용한다.

GUI는 **Python 3.11의 Tkinter/ttk**, 공유 메모리·상태 계산·입력 감시는 기존 **Rust 1.95**를 사용한다. 강화학습은 PyTorch 2.8.0 CPU·NumPy 2.3.3에 Stable-Baselines3 2.7.0·Gymnasium 1.2.0을 추가한다. 별도 실행 환경과 의존성 잠금 파일을 만들고 기존 학습 환경을 보존한다. 해당 SB3 버전의 의존성 범위는 현재 PyTorch·NumPy 버전을 허용한다. [공식 의존성 정의](https://github.com/DLR-RM/stable-baselines3/blob/v2.7.0/setup.py)

GUI와 별개로 강화학습 환경은 새로 구현해야 한다. **작은 관리 화면을 먼저 연결하고, 자동 초기화·강화학습 기능을 차례로 추가한다.**

## 2. 최소 GUI 기능

하나의 창에 작업 선택, 설정, 실행 상태, 최근 결과를 배치한다.

| 영역 | 필요한 기능 |
|---|---|
| 연결 상태 | ACC 연결, 차량·트랙, 공유 메모리 갱신, 경로 추적, vJoy·보정 상태 |
| 작업 선택 | 기록 수집 / 모방학습 / 강화학습 / 평가·주행 |
| 입력 선택 | 검증된 데이터, 경로, 보정 프로필, 모델·체크포인트 선택 |
| 실행 설정 | 학습 횟수·시간 제한, 실행 모드, 사용 가능한 속도 단계 |
| 실행 조작 | 준비, 학습 시작, 중지, 이어서 학습 |
| 진행 상태 | 현재 단계, 회차·epoch·갱신 횟수, 경과 시간, 속도, 보상·손실, 종료 이유 |
| 결과 | 최근 실행 목록, 결과 폴더와 기존 HTML 보고서 열기 |

- 실게임 작업의 `준비` 버튼은 입력 검증 후 **F7 대기**까지만 진행한다.
- 오프라인 학습은 GUI에서 시작하고 중지한다.
- 실게임 작업에서는 `PID 출발 / 모델 제어 / 정지 처리 / 초기화 / 학습 중`을 명확히 표시한다.
- 학습 완료, 중단, 실패, 사용자 확인 필요 상태를 구분한다.
- 실행 중 설정과 모델 선택을 잠근다.
- 보고서가 자동으로 열리거나 알림창이 ACC의 포커스를 빼앗지 않게 한다.
- 세부 학습 계수와 보상 계수는 TOML로 관리한다. 첫 화면에 모든 설정을 노출하지 않는다.

첫 버전에서는 실시간 대형 그래프, 트랙 편집기, 클라우드 학습, 다중 작업, 드라이버 설치 기능을 만들지 않는다. 바탕화면 바로가기로 실행하며, 별도 설치 프로그램은 후속으로 남긴다.

## 3. 프로그램 관리·핫키·자동 초기화

### 기존 모듈 연결

- 공유 메모리는 기존 TelemetryDataServer 라이브러리로 직접 읽는다. 별도의 네트워크 서버를 추가하지 않는다.
- 단독 기록은 DrivingRecorder를 실행한다. 모델 주행에서는 기존 actuator 기록을 사용한다.
- vJoy의 소유와 입력 전송은 Rust 감시기만 담당한다.
- GUI 관리 명령과 실제 주행 명령의 통신 경로를 분리한다.
- 기존 CLI에 선택적인 관리 모드를 추가하여 진행 이벤트·정상 중지·완료 결과를 구조화된 메시지로 주고받는다. 기존 CLI 실행 방식은 유지한다.
- GUI 표시 갱신은 최대 5Hz로 제한하고, 저장·표시 때문에 100Hz 입력 감시가 막히지 않게 한다.

### F7/F8과 종료

관리 모드에서는 Rust 실행 관리자가 핫키를 단독 등록한다. 자식 프로그램의 중복 등록을 막는다.

- **F7:** 준비된 기록·주행 또는 제한된 자동 학습 묶음을 시작한다.
- **F8:** 현재 동작과 예약된 다음 회차를 모두 취소한다.
- 강화학습에서는 최초 F7 이후 정상적인 회차 종료에 한해 자동 초기화·다음 회차를 허용한다.
- F8, 전면 이탈, 통신·저장·장치 오류 뒤에는 자동 재출발하지 않는다.
- GUI 종료·프로세스 연결 단절도 감시기에 중지 요청으로 전달한다.
- 주행 중 종료는 기존 가속 해제·제동·정지 확인·입력 해제 절차를 따른다. 감시기를 강제로 종료하여 정상 종료로 표시하지 않는다.
- 학습 중지는 완료된 저장 단위를 보존한다. 이어서 학습은 새 실행 폴더에서 시작한다.

### ACC 자동 초기화

첫 지원 조건은 **BMW M4 GT3 / Brands Hatch / 핫랩 / 현재 PC의 고정된 화면·언어 설정**이다.

1. 최초 설정 과정에서 세션 재시작 메뉴와 확인·주행 화면을 등록한다.
2. 화면 확인을 동반한 키보드·마우스 입력으로 세션을 재시작한다.
3. 새 텔레메트리에서 차량·트랙·세션, 시작 위치·방향, 정차 상태를 확인한다.
4. 추적·특징 이력·랩 판정을 초기화하고 다음 회차를 준비한다.

고정 시간만 기다리고 클릭하는 방식은 사용하지 않는다. 메뉴 화면과 텔레메트리 확인이 모두 필요하다. 주행 화면과 메뉴에서 게임 상태값이 같았던 기존 사례도 반영한다.

초기화 검증은 먼저 **학습 없이 3회 연속** 수행한다. 화면 불일치, 로딩 시간 초과, 예상과 다른 출발 위치가 발생하면 반복을 중단한다. 게임 메모리에 위치나 차량 상태를 쓰는 방식은 사용하지 않는다.

## 4. 기존 데이터 활용과 강화학습

### 이미 확보한 데이터 재사용

추가 사람 주행을 선행 조건으로 삼지 않는다.

| 자료 | 사용 방식 |
|---|---|
| 사람 학습용 1·3·4·5·9번 랩 | 경로·구간별 속도·제동 패턴의 기준 |
| 사람 validation 1랩·test 3랩 | 기존 분리를 유지한 별도 검증·비교 |
| 기존 저속 한 바퀴와 교사 주행 | 실제 vJoy 요청값을 이용한 초기 정책 학습 |
| 새 자동 주행 | 강화학습 경험 수집 |
| 새 평가 주행 | 가중치 갱신 없이 성능 측정 |

사람 기록의 `steering_raw`를 vJoy 조향 정답으로 직접 사용하지 않는다. 현재 자료에서는 **사람의 고속 주행 기준**과 **실제 요청값이 있는 저속 제어 자료**를 구분하여 활용한다.

기존 가감속 모델은 보존한다. 새 조향 포함 정책은 교사 기록에서 조향·가감속 요청값을 다시 연결하여 학습한다. 기존 1출력 모델을 수정 없이 SAC에 불러오지 않는다.

### 환경과 정책

- Gymnasium의 `reset / step` 규약으로 실제 관측과 행동 적용 구간을 연결한다.
- 특징 계산과 배포 정책 추론은 Rust에서 공유한다.
- 정책 결정은 기본 **50Hz**, 장치 갱신·감시는 **100Hz**로 한다.
- 행동은 정규화된 조향과 부호 있는 가감속의 두 값이며, 이를 조향·가속·브레이크 세 축으로 변환한다. 가속과 제동은 동시에 요청하지 않는다.
- 새 관측에는 기존 경로 상태·속도 이력에 이전 전송값, 기어, 변화율, 최대 320m 전방 경로·속도 정보를 추가한다.
- 특징·행동·정규화 규약을 새 버전으로 분리한다. 기존 모방 모델의 입력 규약은 변경하지 않는다.
- SAC는 은닉층 128개 두 층, 두 critic, 배치 256, 학습률 0.0003, replay buffer 200,000, seed 42를 기본값으로 한다.
- 초기 정책의 평균 행동을 기존 교사 요청값으로 사전학습하고, critic은 새로 학습한다.
- **주행 중에는 정책을 고정하고, 정지·초기화 대기 중에 가중치를 갱신한다.** 회차당 갱신은 새 경험 수의 1/4, 최대 2,000회로 제한한다.

SAC 구현과 저장·재개 기능은 기존 라이브러리를 활용한다. [SAC 공식 문서](https://stable-baselines3.readthedocs.io/en/v2.7.0/modules/sac.html)

### 반복·보상·평가

한 학습 회차는 다음 순서다.

**자동 초기화 → 출발 준비 → 모델 주행 → 종료·정지 → 경험 검증 → 학습·저장 → 다음 회차**

- 출발 준비는 기존 제어기를 사용하되, 완주 평가에서는 첫 출발선 전에 모델로 인계한다.
- 이후 모델이 조향·가감속을 담당한 유효한 출발선 간 한 랩을 완주로 인정한다.
- 회차 제한은 기본 30분이다. 묶음 전체는 최대 10회 또는 2시간이며 초기화·학습 시간도 포함한다.
- 보상은 정상적인 전진 거리, 소요 시간, 경로·방향 오차, 입력 변화와 유효 완주를 사용한다.
- 후진·순간이동·재시작·출발선 wrap으로 진행 보상이 부풀려지지 않도록 기존 연속성 검사를 적용한다.
- 게임의 랩 무효 판정, 학습 과제 실패, 시스템 오류를 구분한다. 기록에 없는 접촉 원인을 확정하지 않는다.
- 시간 제한은 `truncated`, 과제 성공·실패는 `terminated`로 구분한다. 다음 관측을 확보하지 못한 전이는 만들어 넣지 않는다. [Gymnasium 종료 규약](https://gymnasium.farama.org/tutorials/gymnasium_basics/handling_time_limits/)

속도 목표는 **10 → 20 → 40 → 80 → 120 → 160 → 200 → 240km/h 상한 단계**로 확장한다. 구간 목표는 사람 학습 자료의 속도 기준을 해당 상한으로 제한하여 만든다.

한 묶음에서는 속도 단계를 고정한다. 현재 단계에서 고정 모델로 유효한 3랩 평가를 마쳐야 다음 단계를 선택할 수 있다. 평가 중에는 탐색과 학습을 끄고, 평가 경험은 replay buffer에 넣지 않는다.

고속 RL은 별도 실행 프로필로 관리한다. 기존 저속 시험의 제한을 일괄 해제하지 않는다. 데이터 만료·전면 이탈·F8·저장 오류 등의 중단 규칙은 계속 적용한다.

체크포인트에는 정책·critic·optimizer·경험 버퍼·난수 상태·속도 단계·누적 회차와 입력 해시를 저장한다. 실게임 주행 자체의 완전한 재현성을 보장한다고 표현하지 않는다.

## 5. 개발 순서와 완료 기준

| 순서 | 구현 내용 | 확인할 결과 |
|---|---|---|
| 1 | 실행 관리 규약과 최소 GUI | 기존 기록·학습·평가를 GUI에서 실행·중지·재개 |
| 2 | Rust 관리 모드와 핫키 통합 | ACC 전면에서 F7/F8, 중복 실행 차단, 정상 종료 |
| 3 | 자동 초기화 | 학습 없이 3회 연속 재시작·시작 상태 확인 |
| 4 | 기존 데이터 재사용·새 정책 사전학습 | 출처·집합 보존, 조향 포함 정책의 Python/Rust 대조 |
| 5 | 강화학습 수집·갱신·저장 연결 | 제한된 자동 묶음과 체크포인트 재개 |
| 6 | 완주와 속도 단계 평가 | 유효 완주율·랩타임·오차·중단 이유 비교 |

검증에는 다음을 포함한다.

- 모의 프로세스로 GUI 멈춤, 자식 종료, 핫키 충돌, 통신 단절, 저장 실패 검사.
- 화면 인식 실패와 초기화 시간 초과 시 다음 주행 차단.
- 관측·행동 시간 대응, 이력 초기화, 보상 wrap, 종료·시간 제한 구분.
- 데이터 분리·원본 해시 보존, 평가 데이터의 학습 유입 차단.
- Python/Rust 정책 출력 대조, 저장·재개와 난수 상태 복원.
- 기존 Rust·Python 회귀 검사와 실제 수행한 검사 수 기록.
- 실게임 F8·전면 이탈·자동 초기화·횟수 및 시간 제한 종료 확인.

개발 문서는 Docs에 GUI 실행 규약과 개발 기록을 추가하고, 기존 체크리스트에 GUI·자동 초기화·강화학습·주행 성능 항목을 나누어 기록한다.

**프로그램 동작 완료와 주행 성능 달성을 구분한다.** GUI에서 전체 흐름이 작동하더라도, 고속 유효 완주와 속도 향상은 실제 평가 결과가 있어야 완료 처리한다. 기존 장치 장애 대응 보완은 사용자가 정한 후속 과제로 유지한다.
